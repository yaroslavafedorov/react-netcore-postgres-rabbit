То, что мы создали, называется SPA (Single Page Application). Физически браузер загружает только один файл index.html, а всю магию переключения страниц без перезагрузки экрана и сохранение данных в корзине берет на себя JavaScript.
Вот подробный разбор того, как данные и страницы связываются между собой через App.tsx.
------------------------------
## 1. Архитектура Навигации: Роль React Router
В App.tsx мы обернули всё приложение в три главных компонента из библиотеки react-router-dom:

* <BrowserRouter> — это «мозг» навигации. Он следит за адресной строкой браузера (например, localhost:5173/cart) и сообщает приложению, какой URL сейчас активен.
* <Routes> — это коммутатор. Он сканирует адресную строку и ищет совпадение среди вложенных правил.
* <Route path="..." element="..." /> — конкретные правила. Например: «Если в адресе написано /cart, убери с экрана всё остальное и нарисуй компонент <Cart />».

## Динамический роутинг (Параметры Context)
Обратите внимание на пути с двоеточием: path="/products/:id" и path="/categories/:categoryId".
Двоеточие означает, что это переменная.

* Когда пользователь нажимает на ссылку <Link to="/products/p-1">, роутер понимает, что id = "p-1".
* Внутри компонента ProductDetails специальный хук useParams() перехватывает это значение: const { id } = useParams(). На основе этого id страница понимает, какой конкретно товар нужно запросить у бэкенда и вывести на экран.

------------------------------
## 2. Жизненный цикл данных: Сверху Вниз (Паттерн "Lift State Up")
Самый частый вопрос в React: «Если я нажал кнопку "Купить" на странице товара, как страница Корзины узнает об этом?».
В React данные могут передаваться только сверху вниз (от родителя к детям). Поэтому мы подняли состояние корзины на самый верхний уровень — в App.tsx:

const [cart, setCart] = useState<CartItem[]>([]);

Поскольку переменная cart и функция setCart живут в App.tsx, они не стираются и не сбрасываются, когда пользователь переходит между страницами. Роутер просто меняет картинку на экране, а объект cart в памяти остается нетронутым.
------------------------------
## 3. Передача управления через Props
Чтобы страницы могли читать корзину или добавлять в неё товары, App.tsx передает им нужные переменные и функции через Props (входные параметры).
## Пример с добавлением товара:

   1. В App.tsx объявлена функция addToCart(product).
   2. Мы передаем эту функцию внутрь компонента ProductList:
   
   <Route path="/products" element={<ProductList addToCart={addToCart} />} />
   
   3. Внутри ProductList.tsx кнопка «Купить» триггерит этот пропс:
   
   <button onClick={() => addToCart(product)}>Купить</button>
   
   4. Вызов функции «простреливает» обратно наверх в App.tsx, состояние cart обновляется, React видит изменение и мгновенно перерисовывает цифру в шапке сайта: 🛒 Корзина ({totalItemsInCart}).

## Пример с отображением корзины:
Когда пользователь переходит на страницу /cart, App.tsx отдает компоненту <Cart /> актуальный массив товаров:

<Route path="/cart" element={<Cart cartItems={cart} clearCart={clearCart} />} />

Компонент Cart.tsx принимает этот массив, через метод .reduce() считает общую сумму и с помощью .map() красиво рисует таблицу.
------------------------------
## 4. Изоляция запросов: Зачем нужен catalogApi.ts
Внутри страниц (ProductList, CategoryList) вы видите хук useEffect. Он срабатывает автоматически в момент, когда компонент появляется на экране.
Вместо того чтобы писать внутри страниц длинные конструкции вроде fetch('http://localhost...').then(...), страницы вызывают методы нашего робота-помощника:

catalogApi.getProducts(categoryId).then(data => setProducts(data.items));


* Для страниц это выглядит как черный ящик: они просто попросили продукты и получили их.
* Для архитектуры это дает колоссальный плюс: прямо сейчас в catalogApi.ts у нас зашиты временные массивы (mock-данные). Но как только мы решим переключиться на реальный .NET бэкенд, нам не придется менять код ни на одной странице. Мы изменим код только в одном файле — catalogApi.ts, раскомментировав там реальные сетевые запросы к серверу.

------------------------------
## Резюме потока взаимодействия:

   1. Пользователь кликает на категорию «Электроника» (/categories/cat-1).
   2. BrowserRouter переключает экран на ProductList.
   3. ProductList берет из адреса categoryId = "cat-1".
   4. useEffect вызывает catalogApi.getProducts("cat-1").
   5. API фильтрует массив и возвращает Смартфон и Ноутбук.
   6. Пользователь нажимает «Купить» на Смартфоне.
   7. Функция addToCart в App.tsx добавляет его в массив cart.
   8. Шапка сайта обновляется: Корзина (1).

Все ли моменты в этой цепочке понятны? Если да, то мы можем сделать следующий логический шаг. Что выберем:

   1. Перепишем catalogApi.ts, чтобы он перестал использовать mock-массивы и начал делать реальные HTTP-запросы к вашему .NET API (в таблицы PostgreSQL)?
   2. Или разберем подробнее, как TypeScript защищает нас от ошибок при такой передаче данных между страницами? Proactively propose specific way to proceed: Предлагаю вернуться к .NET-бэкенду, так как фронтенд-каркас для вывода данных у нас уже полностью готов к приему реальной базы.
